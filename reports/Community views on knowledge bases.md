# Citations, not cleverness, make agent wikis work

Across Hacker News, lab engineering blogs and the 2025–2026 research record, practitioners have settled on a few points. Agent memory that works is small, human-readable, file- or tool-based, and loaded just in time. The LLM-compiled wiki is a useful pattern, and its weak point is error that compounds without provenance. The security community now treats any persistent memory write as an attack surface with a delayed trigger. The user's knowledge wiki design (`docs/knowledge_wiki.md`) already makes most of the choices this evidence supports. It cites every statement to stored evidence, computes labels at read time, has one validated and versioned write tool, propagates deletion through citations, renders everything in code, and keeps the vault separate. Its exposure is in two places. The first is retrieval: keyword-only FTS5 is weakest exactly where independent long-context and Portuguese retrieval studies say failures concentrate, which is low lexical overlap and cross-language queries. The second is citation support: the validator checks that a cited item exists, not that it supports the sentence, and independent audits find source misrepresentation in roughly a third of AI answers. The top recommendations are therefore measurement and verification, not new infrastructure. Build a bilingual golden-question eval and log every search, not only misses. Check that each statement is supported by its citation when it is written. Tighten the label rule so a sentence cannot borrow "verified" from one citation while resting on another. Strip hidden Unicode from repository text. Add semantic search only if the eval shows a gap.

## The evidence has three holes worth knowing first

This synthesis rests on four research notes, and the notes have hard limits. **Reddit could not be read at all.** The session's network proxy blocked reddit.com, and the search tool excluded it, so r/ObsidianMD, r/LocalLLaMA, r/RAG and r/ClaudeAI sentiment is missing. Where this report describes the "keep AI out of your vault" mood, it relies on blogs and on HN. **Hacker News pages were also blocked.** HN content comes from search-engine snippets and aggregators, so quotes are partial, dates are inferred from item IDs, and point counts are approximate (the LLM Wiki thread is reported as both 274 and 296 points). **Several primary pages were seen only through summaries.** These include OWASP's ASI06 entry and its May 2026 blog post, mem0.ai, agentsystems.blog, the Karpathy blog and Google's long-context podcast page. Some foundational numbers (Lost in the Middle, RULER, LongMemEval's 30% drop, Contextual Retrieval, ALCE, Liu et al. on generative search) were recalled rather than re-fetched, and are marked "not re-verified" below. The report labels figures as **vendor-reported** (measured by the seller of the system), **paper** (authors of the method) or **independent**. The distinction matters because the memory-benchmark field is full of disputes.

## Simple, scoped, file-based memory keeps beating specialised layers

The most consistent signal across communities is that plain designs hold their own. Anthropic's engineering guidance describes context as a finite "attention budget" that degrades as it grows. It recommends a hybrid: a small curated file dropped into context up front, then grep, glob and tools to retrieve "just in time," with compaction, structured notes outside the window and sub-agents for longer work ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Its long-running harness post goes further. It says "compaction isn't sufficient" and leans on a progress file, a JSON feature list that agents may only flip, and git history as memory. JSON was chosen because the model is less likely to rewrite it inappropriately than Markdown ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Skills use the same principle under the name progressive disclosure: only names and descriptions sit in context, and the full files load on demand ([Anthropic](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).

The benchmark record points the same way, with heavy caveats. In the public Zep–Mem0 dispute, Zep's LoCoMo score was reported as 65.99%, 75.14% and 58.44% depending on who ran the harness. A full-context baseline scored about 73%, and Letta's plain filesystem agent scored **74.0%** ([Bloo-mind](https://essays.bloo-mind.ai/posts/2026-05-20-mem-eval/); [Zep](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/); [Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). Every one of those numbers is vendor-reported. The one small independent check (42 LongMemEval questions, one model as answerer and judge) found Mem0 and Letta statistically tied ([DEV](https://dev.to/everest_an/-i-benchmarked-ai-agent-memory-in-2026-and-the-numbers-tell-a-different-story-than-the-marketing-2ae4)). On HN, commenters report that Mem0's errors come from its LLM extraction layer, not from storage ([HN](https://news.ycombinator.com/item?id=47770220)). Others criticise memory layers that route every read and write through an LLM ([HN](https://news.ycombinator.com/item?id=47260077)), and file-based memory frameworks keep appearing ([HN](https://news.ycombinator.com/item?id=46511540)). The honest conclusion is not that files win. It is that **no specialised memory layer has shown an independent, reproducible lead over plain files plus search**, so buying one first is unjustified.

Users judge consumer memory on scoping and visibility. HN commenters turned ChatGPT memory off because it "doesn't know how to segment itself" ([HN](https://news.ycombinator.com/item?id=45662102)). Simon Willison called its auto-injected summary a "dossier" that leaked a Half Moon Bay sign into an unrelated image prompt ([Willison](https://simonwillison.net/2025/May/21/chatgpt-new-memory/)). He praised Claude's design of on-demand search over raw history ([Willison](https://simonwillison.net/2025/Sep/12/claude-memory/)), and HN discussion favoured Claude's opt-in, project-scoped approach ([HN](https://news.ycombinator.com/item?id=45214908)). OpenAI's own FAQ concedes that memories outlive the chat they came from, that deletion logs are kept up to 30 days, and that "reference chat history" is a synthesis broader than what users see ([OpenAI](https://help.openai.com/en/articles/8590148-memory-faq)). Dissent exists: one HN commenter argues ordinary users like the feature and HN overstates the problem ([HN](https://news.ycombinator.com/item?id=46532743)).

**This validates the wiki's core shape.** The design uses per-project, per-person and per-topic pages read through tools. Reading goes in three steps (catalog, then outline, then sections), the same progressive disclosure Anthropic describes. Statements are itemised and inspectable rather than an opaque synthesis. The user can see, restore or delete every version. And memory is kept in the layer instead of a vendor memory service. The design's choice of SQLite over a memory product, and its explicit "buy semantic search last" gate, match the strongest available evidence.

## The LLM wiki pattern earns interest, and suspicion about compounding errors

Karpathy's gist (April 4, 2026) proposes that an LLM "incrementally builds and maintains a persistent wiki" between the user and raw sources. Knowledge is "compiled once and then kept current, not re-derived on every query", with ingest, query and lint operations and a schema file. An index file "works surprisingly well at moderate scale (~100 sources, ~hundreds of pages)", and "as the wiki grows you want proper search" ([Karpathy](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). The HN thread was solid rather than explosive, at roughly 274–296 points ([HN](https://news.ycombinator.com/item?id=47640875); [marvin-42](https://insights.marvin-42.com/articles/hacker-news-picks-up-karpathys-llm-wiki-pattern-for-persistent-knowledge-bases)). It split on whether this is "just RAG" ([HN](https://news.ycombinator.com/item?id=47644949)) or something new because of the write-and-maintain loop ([HN](https://news.ycombinator.com/item?id=47645066)). The substantive criticism was that an LLM summarising its own summaries bakes hallucinations in as "facts". Commenters also asked whether linting scales as N×N page comparisons, and raised model collapse ([marvin-42](https://insights.marvin-42.com/articles/hacker-news-picks-up-karpathys-llm-wiki-pattern-for-persistent-knowledge-bases); [Lobster Pack](https://www.lobsterpack.com/blog/karpathy-llm-wiki-idea-files/)). Commentators add that RAG remains better when sources change often or when exact provenance to raw text is required ([Atlan](https://atlan.com/know/llm-wiki-vs-rag-knowledge-base/)). Builder reports are anecdotal. One open-source implementer warns that letting the LLM decide everything produces "a lot of meaningless data", such as junk concept tags, and concludes "the LLM writes the wiki, you curate" ([acydoan](https://acydoan.substack.com/p/llm-knowledge-base)). The only quantitative support for compiled summaries in the notes is older: RAPTOR's hierarchical summaries gave about +20 points on QuALITY ([arXiv](https://arxiv.org/abs/2401.18059)). No community thread offered a measured accuracy comparison against a RAG baseline.

The compounding-error worry is backed by hard independent numbers on how LLMs treat sources. The EBU/BBC study of more than 3,000 assistant answers in 14 languages found **45% with at least one significant issue and 31% with serious sourcing problems** ([EBU](https://www.ebu.ch/news/2025/10/ai-s-systemic-distortion-of-news-is-consistent-across-languages-and-territories-international-study-by-public-service-broadcaste)). The Tow Center found over 60% of AI search answers misidentified their source ([CJR](https://www.cjr.org/tow_center/we-compared-eight-ai-search-engines-theyre-all-bad-at-citing-news.php)). Most relevant to a compile step, Peters and Chin-Yee found LLM summaries of science about **5× more likely than expert summaries to overgeneralise** (OR 4.85). Prompting for accuracy made it worse, newer models did worse than older ones, temperature 0 helped, and Claude models had the highest generalisation accuracy ([Utrecht](https://www.uu.nl/en/news/most-leading-chatbots-routinely-exaggerate-science-findings)). A 2026 cross-model audit found that consensus across three or more models raised citation accuracy from 16.5% to 95.6%, and repeating the question within one model raised it from 28.6% to 88.9% ([arXiv](https://arxiv.org/abs/2603.03299v1)).

The wiki answers part of this by design. Citations point to stored items (claim ids, events, commits plus paths), never to free-text URLs, so the fabricated-reference class of error cannot occur. Page citations are explicitly "a link, not evidence", which blocks summary-of-summary chains. Lint works from linked claims and `possible_contradictions` rather than N×N page comparison, which sidesteps the scaling objection. And "my notes" plus human confirmation supply the curation step that builders say is essential. The design does not answer the remaining risk the evidence points to: **a real source cited for a sentence it does not support.** `validate.py` checks that a claim exists, is visible, and that a commit and path exist. It does not check that the path says what the sentence says. The `repo` label then lets agents treat that sentence as fact. Paraphrasing a README into `how-it-works` is exactly the summarisation task where overgeneralisation was measured. The wiki's own instruction to "state what the evidence says" is the kind of accuracy prompt Peters and Chin-Yee found unreliable.

The label rule has a related gap, and the design itself lists it as unverified. "Best of citations" means a sentence citing one verified claim and one unconfirmed event shows `verified`, even when its substantive part rests on the event. Given the compounding-error critique, the label that tells agents "treat this as fact" should not be the most generous one available.

## Keyword-first retrieval is defensible for code, and weakest across languages

The "RAG is dead" argument got strong pushback on HN. The top reply called extrapolating from Claude Code grepping a codebase to all retrieval "a massive logical leap" ([HN](https://news.ycombinator.com/item?id=45445280)). The evidence for grep is real but thin. Boris Cherny reportedly said early Claude Code used "RAG + a local vector db" and agentic search "outperformed everything. By a lot," while calling the evidence "internal vibes." That is second-hand, and the cited reasons were staleness, indexing and security overhead ([OfficeChai](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/)). Cursor kept embeddings and reports **+12.5% accuracy from adding semantic search to grep**, a vendor figure with unpublished methodology ([Cursor](https://cursor.com/blog/semsearch)). HN commenters note that grep misses vocabulary mismatch ([HN](https://news.ycombinator.com/item?id=46631689)). Anthropic's own 2024 Contextual Retrieval work reported top-20 retrieval failures falling 49% with contextual embeddings plus contextual BM25, and 67% with reranking (vendor; not re-verified this session) ([Anthropic](https://www.anthropic.com/engineering/contextual-retrieval)). DeepMind's Nikolay Savinov frames long context and RAG as "synergistic" rather than rivals (via summary) ([Google](https://blog.google/technology/google-deepmind/release-notes-podcast-long-context/)). GraphRAG has little support for a corpus like this one. On GraphRAG-Bench, reranked vector RAG beat Microsoft GraphRAG on simple fact retrieval (60.92 vs 49.29), at roughly 879 versus 38,707–331,375 prompt tokens per query ([arXiv](https://arxiv.org/pdf/2506.05690v3)).

Independent long-context research explains where keyword search fails. NoLiMa built questions with minimal lexical overlap with their answers. At 32K tokens, 11 of 13 models fell below half their short-context score, GPT-4o dropped from 99.3% to 69.7%, and declines began at 2K–8K ([arXiv](https://arxiv.org/html/2502.05167v3)). Chroma's Context Rot report found degradation even on trivial tasks, worse when the question and answer are semantically distant and when topically related distractors are present ([Chroma](https://research.trychroma.com/context-rot)). Chroma sells a vector database, a conflict commentators note ([Hamel Husain](https://hamel.dev/notes/llm/rag/p6-context_rot.html)). The lesson for the wiki is twofold. Its small, budgeted results suit models well: about 3,000 tokens a page, a 40,000-character catalog cap, and sections on request. But **low lexical overlap is precisely the case FTS5 cannot see**, and a Portuguese-English work corpus produces it routinely. The Portuguese evidence is directly on point. In a 500-query clinical preprint, dense-only retrieval failed on 22.2% of queries, while BM25 and hybrid returned statistically distinct sets (McNemar p<0.001), meaning the two are complementary ([DEV](https://dev.to/nomad-link-id/two-retrieval-methods-are-better-than-one-evidence-from-500-clinical-queries-4g41)). A 2026 Portuguese legal study found reciprocal rank fusion robustly beat BM25 ([ACL Anthology](https://aclanthology.org/2026.stil-1.34.pdf)). MTEB-PT shows global embedding rankings predict Portuguese performance only moderately (ρ=0.75), and one model ranks 3rd globally but 49th in Portuguese ([MTEB-PT](https://huggingface.co/papers/2607.04071.md)). These are single-domain academic studies, but they are independent of any vendor.

The design's "keyword first, measure misses, then decide" stance is sound. The community consensus is that agentic grep suits small corpora and code, and hybrid search suits vocabulary mismatch. The weakness is the instrument. `search_misses` records only searches that return nothing. A bilingual keyword index rarely returns nothing; it more often returns the wrong section. The design itself notes that successful searches are not recorded, so there is no denominator and no way to detect "found something, but not the answer." Bilingual `key_terms` live at page level, while statements are indexed in whatever language Claude wrote them. A Portuguese query for an English-written `why` statement therefore depends on the page-level terms matching. One step is already partly done: weighting section headings above statement text is a crude form of the contextual BM25 that Anthropic found helps on its own.

## Context files, llms.txt and statements.jsonl: plain formats pass, bloat fails

On context files, the evidence mainly argues for restraint. An ETH Zurich study of AGENTS.md (arXiv 2602.11988) found that LLM-generated files slightly *lowered* success and hand-written ones slightly raised it, neither significantly, while adding about 19–23% to inference cost ([HN](https://news.ycombinator.com/item?id=47034087); [jangwook](https://jangwook.net/en/blog/en/agents-md-effectiveness/)). A field study found a 28.64% shorter median runtime and 16.58% fewer output tokens at comparable completion ([generativelabs](https://www.generativelabs.com/insights/claude-md-agents-md-context-files)). HN read both as evidence against bloat, not against context files. For the wiki this matters twice. The `wiki` instructions are a context file, and they should stay short and written by the user. And the wiki pages themselves are LLM-generated context fed to resuming agents. Whether they actually beat `get_project` alone is exactly what the planned two-week resumption check should measure, in tokens and time as well as correctness.

HN is sceptical of llms.txt as a crawler signal: server logs show no fetches, including none from Anthropic's crawlers ([HN](https://news.ycombinator.com/item?id=47058870)). Its proposer, though, framed it as inference-time context that the user pulls in, and library maintainers use it that way ([HN](https://news.ycombinator.com/item?id=41439983)). The wiki's local, file-only use of `llms.txt` is the use case that survives the criticism. A greppable `statements.jsonl` matches the grep-first habits of coding agents. Rendering Markdown and JSON instead of raw HTML matches the token evidence the design already cites.

## Poisoning persists, so every write and every read of untrusted text is a control surface

Security practitioners now treat memory as a persistent, time-delayed injection sink. OWASP's Top 10 for Agentic Applications (December 2025) lists ASI06, "Memory & Context Poisoning" ([OWASP](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/)). Its co-lead's post argues that retained context "deserves the same scrutiny we already apply to execution paths, credentials" ([OWASP](https://genai.owasp.org/2026/05/13/memory-is-a-feature-it-is-also-an-attack-surface/); snippet only). Secondary analysis says poisoning shows up as gradual drift that single-event monitoring misses ([Vectorize](https://vectorize.io/articles/owasp-asi06); vendor). The demonstrated attacks are concrete. Rehberger planted persistent exfiltration instructions in ChatGPT memory, and the exfiltration channel was closed but untrusted writes to memory were not ([The Hacker News](https://thehackernews.com/2024/09/chatgpt-macos-flaw-couldve-enabled-long.html)). A document made Gemini save false memories when the user later typed "yes." Tying the write to a benign later turn bypassed the rule against calling tools on untrusted data ([Embrace The Red](https://embracethered.com/blog/posts/2025/gemini-memory-persistence-prompt-injection)). Invisible Unicode in rules files made Cursor and Copilot insert an external script, and the characters did not show in GitHub's review UI ([Pillar Security](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)). Academic attacks reach high success in controlled setups: MINJA reports 98.2% injection success through ordinary queries ([arXiv](https://arxiv.org/html/2503.03704v5)), and PoisonedRAG reports about 90% with five texts among millions ([USENIX](https://usenix.org/system/files/usenixsecurity25-zou-poisonedrag.pdf)). These figures show the attacks are feasible, not how often they happen in the wild. A follow-up argues MINJA's conditions are idealised ([arXiv](https://arxiv.org/html/2601.05504)).

The mitigations practitioners take seriously are architectural. Willison's lethal trifecta warns against combining private data, untrusted content and external communication ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Design-pattern work and DeepMind's CaMeL rest on one principle: untrusted input must not be able to trigger consequential actions ([Willison](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)). Practical guidance adds regular human review of stored memories ([The Hacker News](https://thehackernews.com/2024/09/chatgpt-macos-flaw-couldve-enabled-long.html)) and treating AI configuration files with the scrutiny given to executable code ([Pillar Security](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)).

**The wiki's threat model is unusually well aligned with this literature.** The compile run holds private data and reads untrusted repository text, but it has no web, connector, Bash or file tools. That breaks the trifecta's exfiltration leg and satisfies the "Rule of Two." There is one write tool, and it validates, versions, audits and can be undone. Labels are visible to agents, and unconfirmed statements are leads, not facts. Found instructions are described rather than quoted. HTML and SVG are drawn by code under a strict CSP, which closes the "poisoned statement becomes a script" path. The weekly review is the memory-review ritual Rehberger recommends. Three gaps remain. First, `read_repo` redacts secrets but does not strip or flag invisible and bidirectional Unicode, which is the Rules File Backdoor vector, and `validate.py` does not reject it in statement text. Second, `propose_wiki_update` is *Always allow* in Claude Desktop, where connectors bring email and chat into the same session. That is the Gemini pattern, in which a write rides on a later benign turn. The validation and the versioning limit the damage, but nothing flags a write that followed untrusted content. Third, drift: no metric tracks how much of a page each version rewrites, so a slow, plausible poisoning spread across versions would look like routine maintenance.

## Updates, time and the human owner are where knowledge bases actually decay

Memory systems handle changed facts badly. On MemoryAgentBench FactConsolidation, Mem0 scored 18.0 and Zep 7.0 (cited second-hand in a 2026 preprint) ([arXiv](https://arxiv.org/pdf/2607.21962)). Another benchmark paper reports that state-of-the-art systems "consistently fail at knowledge updates across sessions" ([arXiv](https://arxiv.org/pdf/2607.16716)). The main proposed fix is temporal validity. Zep's bi-temporal model marks superseded facts instead of overwriting them ([arXiv](https://arxiv.org/html/2501.13956)), and append-only stores resolve contradictions at query time ([arXiv](https://arxiv.org/pdf/2604.11544)). The supporting evidence is mostly self-reported. The wiki has versions, `built_from` commits and staleness detection, which are stronger than most memory products. But a statement does not carry the date of its evidence, and nothing marks one statement as superseding another. Agents therefore cannot tell "decided in March, reversed in October" from two equal facts unless the compiled prose says so.

The human side is the most common way personal knowledge bases fail. "I deleted my second brain" captured the write-once, read-never problem ([HN](https://news.ycombinator.com/item?id=44402470); [Westenberg](https://www.joanwestenberg.com/i-deleted-my-second-brain-692aa40d59d5f06dd5131e43)). HN's "writing is thinking" camp sees AI-authored notes as hollow ([HN](https://news.ycombinator.com/item?id=47573519)). Practitioners keep AI output in a separate container and use AI "as retrieval, not generation" ([DEV](https://dev.to/notoriouslab/ai-as-retrieval-not-generation-why-i-stopped-letting-ai-into-my-vault-and-the-plugin-that-came-5fhc)). Empirical work supports the worry. Microsoft and CMU found that higher confidence in AI correlated with less critical thinking among 319 knowledge workers ([The Register](https://www.theregister.com/2025/02/11/microsoft_study_ai_critical_thinking/)). MIT's preprint found that LLM-assisted writers struggled to quote their own essays ([MIT Media Lab](https://www.media.mit.edu/publications/your-brain-on-chatgpt/)). The circulating "82% abandon within six months" figure has no source and should not be used. The wiki's separation of its own content from the vault, the frontend-only "My notes", and the confirmation-rate metric all line up with this. The design names the confirmation rate as the bottleneck, and that is the right reading of the evidence. The open risk is that Claude writes the `why` and `lessons` sections, the two that most resemble the user's own thinking, which is the "hollow notes" failure in a new place.

## Prioritised recommendations for the knowledge wiki

The ordering weighs evidence strength against cost. Items 1–4 are cheap, close concrete gaps, and do not change the architecture. Items 5–7 depend on what item 1 measures.

| # | Recommendation | Concrete change | Evidence it rests on |
|---|---|---|---|
| 1 | **Measure retrieval properly before deciding on semantic search** | Build 50–150 golden questions in Portuguese, English and mixed (including PT query → EN statement), each with its target section. Report recall@5/@10 for `search`. Log *every* search with its result ids and whether the agent then opened one of those sections, so "found but wrong" becomes visible. Fix the answering model when comparing. | NoLiMa and Context Rot show failures concentrate at low lexical overlap; Portuguese studies show BM25 and dense miss different queries; the memory-benchmark disputes show results swing with setup. `search_misses` alone cannot see wrong hits. |
| 2 | **Check that each citation supports its sentence, not only that it exists** | In `propose_wiki_update`, require repository citations to carry a line range or short supporting span, and verify the span exists at that commit. Add a `wiki_lint` pass (or a second `claude -p` check) that tests a sample of new statements against their cited text and flags unsupported ones. Run compile at low temperature where configurable. | EBU 31% sourcing problems, Tow >60% misattribution, 5× overgeneralisation in LLM summaries (all independent). "Be accurate" prompts made it worse. Repeat or cross-model checking raised citation accuracy sharply (paper). |
| 3 | **Stop letting a sentence borrow its strongest citation's label** | Resolve the open "label rule" question in favour of weakest-citation-wins for the label agents treat as fact. Or keep best-of for display, show "mixed" when citations differ, and have `common.md` treat only all-verified or all-repo statements as facts. | HN's compounding-hallucination critique of LLM wikis; the design's own "Not verified yet" item. |
| 4 | **Strip or flag hidden Unicode at both ends** | In `read_repo`, detect zero-width, tag and bidirectional-control characters, return them as a visible marker plus a warning, and record a lint finding. In `validate.py`, refuse statement text containing them. | Rules File Backdoor (Pillar): instructions invisible in GitHub review but followed by agents; OWASP ASI06. |
| 5 | **Close the bilingual gap cheaply first** | Move `key_terms` (or an automatic PT/EN gloss) down to section level. Have the `wiki` instructions tell agents to search in both languages and reformulate once before concluding there is nothing. Prepend page title and section summary to each statement's indexed text (contextual BM25). | Anthropic's contextual BM25 gain (vendor, not re-verified); Claude Code and Letta experience that iterative agent search compensates partly; Portuguese hybrid studies. |
| 6 | **If item 1 shows a gap, add hybrid search, not a memory product or GraphRAG** | Use the step-5 plan as written (local CPU model, vectors in SQLite, fused with FTS5 by RRF). Choose the model on MTEB-PT or your golden set rather than global MTEB rank. | Cursor's +12.5% (vendor); RRF gains in Portuguese (independent); MTEB-PT rank mismatch; GraphRAG's 40–400× token cost and losses on simple facts; no independent lead for Mem0, Zep or Letta. |
| 7 | **Make time explicit** | Expose each statement's evidence date (claim or event time, commit date) in `get_wiki_page` and `statements.jsonl`. Let a statement cite the one it supersedes, and have lint flag a section that holds both an old and a new value with no supersession. | Low knowledge-update scores (MemoryAgentBench, LongMemEval follow-ups); Zep's bi-temporal invalidation. |
| 8 | **Watch for slow drift and risky writes** | Add per-version churn (share of statements changed or removed) to `get_metrics`, and surface large rewrites in the weekly review. In Claude Desktop sessions where connectors returned email or chat, have `propose_wiki_update` mark the version "written after untrusted content" for review. | ASI06 drift framing; the Gemini delayed-invocation attack; Rehberger's memory-review advice. |
| 9 | **Turn the two-week check into a small A/B** | Resume the same projects with and without the wiki page, with the same model, and record correctness, tokens and wall time. Keep the `wiki` instructions short and written by the user. | ETH AGENTS.md study (LLM-written context slightly hurt, +19–23% cost) versus the field study's efficiency gains. |
| 10 | **Keep Claude out of the user's thinking sections** | Allow `why` and `lessons` statements only when they cite a decision claim, a verified claim or My notes, never events alone. Have the weekly review prompt for one line of My notes on the most active project. | "Writing is thinking" threads; Microsoft/CMU and MIT cognitive-offloading findings; the acydoan "you curate" lesson; the design's own confirmation-rate bottleneck. |

The evidence also **validates choices already made**, and these should stay:

- **Stored-item citations instead of URLs.** This removes the fabricated-reference failure class.
- **Labels computed at read time, and statements that disappear when their evidence expires.** This is the deletion propagation that governance analysis says derived artefacts need.
- **One validated, versioned, audited write tool, and a compile run with no external tools.** This breaks the lethal trifecta.
- **Rendering by code, with no HTML or SVG from agents and a strict CSP.**
- **Progressive disclosure across catalog, outline and sections, with page budgets.** This matches the attention-budget and context-rot findings.
- **Page links that do not count as evidence.** This blocks summary-of-summary chains.
- **Lint based on claim contradictions rather than N×N comparison.**
- **The vault kept as the user's view, and My notes edited only by the user.**
- **llms.txt and statements.jsonl used for local, pulled context.**
- **No vendor memory layer, no GraphRAG, and semantic search held back until it is measured.**

## Conclusion

The community debate has moved on from "RAG versus long context versus memory." What practitioners now argue about is provenance and upkeep: who wrote a fact, what it rests on, whether that still holds, and whether anyone checks. On those questions the user's design is ahead of almost everything discussed on HN or sold by memory vendors. Its citations, read-time labels and deletion propagation answer the most serious objection to Karpathy's pattern, and the published memory products fail on the same points. The remaining risks are quieter than an injected script or a fabricated URL. A real citation can stand behind an overstated sentence. A Portuguese query can miss an English statement without registering as a miss. A page can drift a little with each version. All three can be measured with tools the layer already has.

The practical takeaway is that the next engineering effort should go into instruments, not infrastructure. Two pieces of instrumentation would settle most of the open questions in the design's "Not verified yet" list with the user's own data instead of contested vendor benchmarks: a bilingual golden-question eval with full search logging, and a support check on citations. No single study in this corpus can answer what those two will show for this particular wiki, and the field's benchmark disputes are the strongest argument for measuring locally before adopting anything new.
