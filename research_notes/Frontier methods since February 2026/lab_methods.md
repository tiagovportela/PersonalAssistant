## 1. Evaluation: how the labs say to build evals for agents (task design, graders, trajectories vs outcomes, regression vs capability, real failures, statistics, saturation; memory / retrieval / knowledge-work evals)

### Takeaway
Since February 2026 the labs' published eval method has converged on: write down what you measure before you run, grade with atomic pass/fail criteria (code checks where there is ground truth, a separately-prompted and human-validated model judge otherwise), run every case several times and report spread, build cases from real observed behaviour and failures, and compare against a no-intervention baseline. Anthropic also published (6 November 2026) the first lab account of evaluating an LLM-maintained wiki as agent memory, with concrete numbers on when a wiki beats plain search and when it does not.

### Cited Findings

**Anthropic, "Building strong safety evaluations" (13 November 2026)** — written for safety evals but explicitly a general eval-method checklist; all quotes from [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- The three minimum practices: "If you only do three things, do these: write down the construct you want to measure before collecting data, validate your grader against human judgment before trusting any number it produces, and report uncertainty so readers can tell signal from noise." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Construct validity: "what exactly are you trying to measure? This is also called construct validity—whether your measure captures the concept you actually care about—and it’s where AI evaluations often go wrong." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Observational vs causal design: "Causal claims (for example, “This intervention made the model safer”) need a design that varies one variable at a time, such as evaluating the same model with and without a specific intervention in place." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Whole-trajectory grading: "One bad turn—like a model divulging details on how to run a scam when repeatedly pressed—results in a failing grade for the whole conversation." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Measure both failure directions with paired cases: "A good eval also needs to measure both compliance with harmful requests and over-refusal of benign requests. In our single-turn evals, we pair two different kinds of prompts: harmful requests (where we aim to maximize the “harmless response rate”) and benign requests (where we aim to minimize the “refusal rate”) in the same domain." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Cases from real behaviour, kept alive: "Fully invented scenarios tend to be both too easy for models to pass and subtly unlike what real users write, so build from observed behavior whenever possible." and "treat the scenario set as evolving rather than static ... we continuously add and revise cases based on what we find in our enforcement and monitoring work." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Vary dimensions independently: "if you want to understand how the severity of a case and the tone the user employs affect the safety of a response, ensure you’re testing each severity level paired with each type of tone." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Match the eval setup to the deployment: "A model’s willingness to comply with a harmful request can also depend on the environment setup, such as whether it has access to tools or uses the default system prompt, so match the eval setup to the deployment you want to test." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Contamination and shortcuts: "Build from data that postdates the model’s training cutoffs, or use synthetic data you’ve generated yourself." and "Before trusting a score, make sure you’ve closed off any paths that would let the model get full points without completing the task as intended." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Saturation: "the single-turn tasks are saturated, and are therefore useful mainly as regression checks on known failure modes. When an eval saturates, make the tasks harder in ways that preserve the construct (for example, by giving the tasks longer horizons, subtler presentations, or more naturalistic writing) rather than adding trick questions." Also: "Both too-easy and too-hard tasks leave no room to measure differences in model performance." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Code-based graders: "Programmatic checks (such as executable tests, exact matches, and pattern matching) work well when the grader is scoring outcomes with a clear ground truth. But keep an eye out for edge cases." (example given: a pattern match on "Yes" that matches "Yes, I’m generally happy to help, but not with this request.") — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Model-based graders, rubric shape: "Make criteria atomic and binary. Opt for a set of yes/no questions over a single overall score." and "explicitly state what does not meet the criterion to resolve borderline cases rather than leaving them up to the grader’s discretion." and "Spell out what should not change the verdict." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Writing the judge prompt: "imagine you’re writing grading instructions for a competent colleague who hasn’t worked in your area before. Explain the task without jargon and with sufficient specificity." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Grader bias checks: "The grader should only see the conversation and not the surrounding design metadata used to construct it"; "consider using a different model for the grader than the one being tested, since model graders have been shown to recognize and favor their own outputs. Graders also favor longer responses and the first option they are shown in a pairwise comparison, so check whether the grader’s scores correlate with response length, and re-run pairwise comparisons such that the options are flipped." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Test the grader itself: "re-grade a sample of transcripts with a different model or a differently worded rubric, and check that your top-line results hold. If the conclusions change when the grader does, you’ve likely measured the grader, not the model, and need to update it." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Grader failure handling: "Fail loudly. When the grader itself breaks, the item it breaks on should be flagged and excluded from the eval instead of silently scored or dropped." and "graders’ verdicts may change in subtle ways—such as grading more strictly or leniently—when the underlying model changes." and "when a score surprises you, check the eval setup first." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Human validation of graders: "have humans label a sample of the transcripts without seeing the grader’s verdicts, then report the agreement between the human verdicts and the grader’s, corrected for chance." (footnote: "With statistics like Cohen’s kappa"). "Benchmark the agreement between humans and the grader against how well the human labelers agree with each other ... When human reviewers agree with one another but disagree with the grader, treat it as a signal to revisit the rubric." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Preregistration: "Decide how you’re going to analyze the results before you see them ... Write down the main metrics ..., the comparisons you’ll make ..., the data slices you’ll report ..., and the threshold that would count as an improvement or regression. If you deviate from the plan, say so in your report, and explain why." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Sample size and repeated trials: "Model outputs are noisy and nondeterministic, so plan to run each test case several times and report the spread. We treat 100 items as the floor for a complex, multi-turn eval and 1,000 as the floor for a simpler, single-turn one." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Paired comparison: "Small differences between models are easier to detect with paired comparisons, where you run both models on the same items and compute the confidence interval on the per-item differences rather than on each model’s aggregate score." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Report uncertainty; a 4-point gap can be noise: "Claude Opus 5 and Opus 5.5 differed by multiple percentage points (98% versus 94%). However, the difference between the two models wasn’t statistically significant, so we couldn’t conclude that one performed better than the other." Multi-turn confidence intervals "can be wide, exceeding ±10 percentage points." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Report by slice: "Break results out by category (such as sub-area or difficulty) rather than averaging across them, report the category results that didn’t change alongside those that did, and, if you ran many comparisons, correct for that with statistical adjustments." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Document the run: "Provide enough detail (such as model versions, sampling settings, prompts, grader version, and dates) that someone else could reproduce the run, and don’t compare scores from different graders". Configuration matters: API vs claude.ai system prompt differed by "as high as 34 percentage points". — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Evals as a development loop, not a release gate: after transcript review found a problem, "we therefore added an instruction to the system prompt ... Re-running the eval with this and other targeted system prompt mitigations showed that the changes to our system prompt significantly improved the appropriate response rate on claude.ai (60% on the API vs 94% on claude.ai with the new system prompt)." and "it’s also helpful to run evals continuously during the model development process rather than once before release." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Tooling named: "The UK AI Security Institute’s open-source Inspect framework ... handles the mechanics of running, logging, and grading evals, and our Petri toolkit, built on Inspect, automates the kind of multi-turn behavioral testing described here." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Simulated-user method for multi-turn cases: a domain expert writes a specification (objectives, tactics, persona, tone); "The first user turn is fixed, so every run of a scenario starts from the exact same prompt"; "A separate Claude model generates the subsequent “user” turns"; "Each scenario runs a number of times, and each run draws on a different combination of characteristics from the specification"; "A grader model scores each transcript against the risk area’s rubric." — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)

**Anthropic, "The components of agent memory" (6 November 2026)** — memory, wiki and knowledge-work evaluation
- Definition used: "By “agent memory,” we mean knowledge that Claude gains from experience ... and that it retains between sessions, saved as context it can read later." — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- Wiki-as-memory eval design: a corpus of "about 350,000 files, roughly 420M tokens"; "We created an evaluation set of 25 questions about this corpus and gave Claude a search tool to explore it." Agents were prompted over 128 sessions "to explore the files, write or correct linked wiki pages, merge duplicates, and check claims against the sources." Result: "As we scaled dreaming from two sessions to 128, performance on the 25 questions grew from 13% to 48% of graded criteria". — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- Ablation by retrieval arm (wiki only / search only / both): "When it used both search and the wiki, Claude’s aggregate score rose from 54% to 61% as that wiki grew, compared with 53% when it had access to the search tool alone. Claude’s best score was 48% when it used only the wiki to answer questions. Using search and the wiki also saved about 20,000 tokens per question." — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- Where a wiki helps: on 24 merger questions "more than half of which needed Claude to find information across several documents ... Claude scored 87% when it consulted the wiki, compared with 73% when it used search alone." Where it does not: "brief criteria often could be retrieved with a text search from a single document, and the wiki showed no clear gain in performance relative to search." — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- A failure mode measured: "On another LAB task, the wiki grew larger than the documents themselves ... Claude had made an extremely detailed wiki that effectively abstracted nothing." — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- Fact-survival metric: counting how many graded source facts made it into the wiki — "Claude had included only 41 of the 57 facts (72%) ... the shared table summarized the contract terms poorly and was missing some of them altogether, because agents had overwritten one another’s work." After the instructions were rewritten ("Each contract got its own page in the wiki, written by a single agent, which quoted the terms word for word rather than summarizing them into a shared table"), "100% of the criteria could be met, up from 72%." — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- Eval-driven instruction improvement: "we ran a loop in which Claude reflected on its failures, proposed a change to the instructions, and rebuilt the wiki." — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- Memory-with vs stateless baseline: the CL-Bench task was reported as "comparing memory with a stateless baseline across models"; Claude "started each question in a fresh session, with one exception: it could retrieve files from a memory directory that persisted from one session to the next." — [Source](https://www.anthropic.com/research/components-of-agent-memory)
- Behavioural metric from transcripts: "Without being prompted to, it read its memory before answering 9 out of 10 times. By comparison, Sonnet 4.6 did this less than half of the time." — [Source](https://www.anthropic.com/research/components-of-agent-memory)

### Inferences
- (Inference) The existing manual five-day evaluation against hand-written labels is the right raw material; what the 2026 guidance adds is (a) a written, pre-registered metric and pass/regress threshold, (b) each case run at least three times with the spread reported, (c) a no-layer or previous-version baseline arm so a score shows contribution, not just level, and (d) a paired per-item comparison when comparing two prompt/model versions.
- (Inference) For the end-of-day "claims" and the compiled wiki, Anthropic's wiki experiments suggest three cheap, direct metrics: a fixed question set answered from wiki-only / search-only / both; a fact-survival count (how many hand-labelled source facts appear correctly in the page); and wiki size relative to sources as a guard against a wiki that "abstracted nothing". Weight the question set toward multi-source questions, since that is where the wiki showed gain.
- (Inference) The three-level MCP evaluation from the OpenAI cookbook maps directly onto this project: existing unit tests are level 1 (direct tool tests); a small function-calling loop over the 24 MCP tools would be level 2; the actual `claude -p` run with the exact allowlist is level 3. Scores at one level should not be assumed to transfer.
- (Inference) A model judge used on the wiki or claims should use atomic yes/no criteria, be a different model or at least a separately-prompted instance, never see how the case was constructed, be re-checked against the owner's own labels (agreement corrected for chance), and fail loudly on parse errors. With a single human labeller, inter-human agreement cannot be measured, so self-consistency on re-labelling a sample after a gap is the nearest substitute.
- (Inference) With five labelled days the sample is far below Anthropic's stated floors (100 multi-turn / 1,000 single-turn items); results at that size can only catch large regressions, and should be reported with that caveat rather than as percentages to compare.
- (Inference) Saturated cases (always pass) should be kept as a regression suite; new capability cases should come from real failures seen in run transcripts.

## 2. Harness design for long-running and unattended agents (planning, progress files, checkpoints, verification, generator/evaluator, self-critique, multi-agent, when sub-agents help or hurt, cost controls)

### Takeaway
The labs' stated pattern is: give the agent a written plan and a progress file, a verifier it cannot argue with, and a separate evaluator rather than self-critique — then remove each piece of scaffolding when a new model no longer needs it. Multi-agent setups are reported to help on parallelisable or beyond-solo tasks and to hurt (cost, overwritten work, duplicated effort) on coupled ones; explicit budgets and completion conditions are now first-class features.

### Cited Findings

**Anthropic, "Harness design for long-running application development" (24 March 2026)** — all from [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Self-evaluation fails: "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre." — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Separate the judge: "Separating the agent doing the work from the agent judging it proves to be a strong lever to address this issue ... tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work". — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Out of the box the evaluator is weak: "Out of the box, Claude is a poor QA agent. In early runs, I watched it identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway. It also tended to test superficially". — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Gradable criteria (exact text shown in a code span because it contains its own quotation marks): `"Is this design beautiful?" is hard to answer consistently, but "does this follow our principles for good design?" gives Claude something concrete to grade against.` Hard thresholds: "Each criterion had a hard threshold, and if any one fell below it, the sprint failed and the generator got detailed feedback on what went wrong." — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Agree "done" before work: "Before each sprint, the generator and evaluator negotiated a sprint contract: agreeing on what "done" looked like for that chunk of work before any code was written." — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Planner scope: the planner was told "to stay focused on product context and high level technical design rather than detailed technical implementation" because "if the planner tried to specify granular technical details upfront and got something wrong, the errors in the spec would cascade into the downstream implementation." — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- File-based handoff: "Communication was handled via files: one agent would write a file, another agent would read it and respond either within that file or with a new file". — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Cost of the full harness: solo run "20 min", "$9"; full harness "6 hr", "$200" — "The harness was over 20x more expensive, but the difference in output quality was immediately apparent." The later simplified harness: "about 4 hours and $124 in token costs", with a per-phase duration/cost table. — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Simplify methodically: "every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing". After a failed radical cut: "I moved to a more methodical approach, removing one component at a time and reviewing what impact it had on the final result." — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- When an evaluator pays: "the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." For tasks inside that boundary "the evaluator became unnecessary overhead." — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Planner still earned its place: "Without the planner, the generator under-scoped". Residual failure with a stronger model: "The generator was still liable to miss details or stub features when left to its own devices". — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)

**Anthropic, "Building a C compiler with a team of parallel Claudes" (5 February 2026)** — all from [Source](https://www.anthropic.com/research/building-c-compiler)
- The loop: a bash `while true` that runs `claude --dangerously-skip-permissions -p "$(cat AGENT_PROMPT.md)"` with a per-commit log file; "(Run this in a container, not your actual machine)". — [Source](https://www.anthropic.com/research/building-c-compiler)
- Verifier quality is the main lever: "Claude will work autonomously to solve whatever problem I give it. So it’s important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." Tests were added "as I identified those failure modes." — [Source](https://www.anthropic.com/research/building-c-compiler)
- Progress files: "each agent is dropped into a fresh container with no context ... I included instructions to maintain extensive READMEs and progress files that should be updated frequently with the current status." — [Source](https://www.anthropic.com/research/building-c-compiler)
- Design output for the agent: "The test harness should not print thousands of useless bytes. At most, it should print a few lines of output and log all important information to a file so Claude can find it when needed ... if there are errors, Claude should write ERROR and put the reason on the same line so grep will find it. It helps to pre-compute aggregate summary statistics so Claude doesn't have to recompute them." — [Source](https://www.anthropic.com/research/building-c-compiler)
- Time blindness: "Claude can't tell time and, left alone, will happily spend hours running tests instead of making progress." The harness has "a default --fast option that runs a 1% or 10% random sample." — [Source](https://www.anthropic.com/research/building-c-compiler)
- Task locking: "Claude takes a "lock" on a task by writing a text file to current_tasks/". No orchestrator: "I don’t use an orchestration agent." — [Source](https://www.anthropic.com/research/building-c-compiler)
- Where parallel agents hurt: "Unlike a test suite with hundreds of independent tests, compiling the Linux kernel is one giant task. Every agent would hit the same bug, fix that bug, and then overwrite each other's changes. Having 16 agents running didn't help". The fix was an oracle (GCC) that split the task. — [Source](https://www.anthropic.com/research/building-c-compiler)
- Specialised roles: one agent "coalescing any duplicate code", another to "critique the design of the project", another "to work on documentation." — [Source](https://www.anthropic.com/research/building-c-compiler)
- Cost: "Over nearly 2,000 Claude Code sessions across two weeks, Opus 4.6 consumed 2 billion input tokens and generated 140 million output tokens, a total cost just under $20,000." Limit reached: "New features and bugfixes frequently broke existing functionality." — [Source](https://www.anthropic.com/research/building-c-compiler)

**Anthropic, "Long-running Claude for scientific computing" (23 March 2026)** — all from [Source](https://www.anthropic.com/research/long-running-claude)
- Core ideas: "a progress file, a test oracle, an agent prompt with clear rules". — [Source](https://www.anthropic.com/research/long-running-claude)
- Progress file contents: "A good progress file might track current status, completed tasks, failed approaches and why they didn't work, accuracy tables at key checkpoints, and known limitations. **Anthropic, "Scaling Managed Agents: Decoupling the brain from the hands" (8 April 2026)**

### Inferences
- (Inference) For the two unattended runs, the minimum "lab-style" harness is: a rules file, a progress/failed-approaches file the run must read first and update last, a deterministic verifier the run must pass before finishing, and a hard budget. All four are described by Anthropic in February–March 2026 and are independent of any hosted product.
- (Inference) The compile run's "one page per run" design matches Anthropic's fix for lost facts (one writer per page, quote terms verbatim rather than summarise into shared tables). It avoids the overwrite failure reported for shared pages.
- (Inference) A separate reviewer pass over a compiled wiki page or a day's claims (different prompt, fresh context, rubric of atomic checks, hard threshold) is the labs' substitute for self-critique; whether it is worth the cost should be tested by ablation, since Anthropic reports the evaluator becomes "unnecessary overhead" when the task is within what the model does reliably alone.
- (Inference) ADK 2.0's argument (deterministic routing, LLM only for the fuzzy steps) supports keeping scheduling, page selection and validation in Python and using the model only for writing and judging.
- (Inference) Sub-agents are reported to help when work is independent or when isolation keeps the main context small, and to hurt on coupled tasks or shared write targets. A single end-of-day agent writing to one store is a coupled task by that description.

## 3. Context engineering (compaction, memory tools, just-in-time retrieval, progressive disclosure, Agent Skills, tool-result size limits, prompt caching, instruction files)

### Takeaway
The 2026 material treats context as a hierarchy: a small always-loaded layer that acts as an index, larger material read on demand, and a durable log outside the context window that can be re-queried. Compaction is now a server-side API feature at both Anthropic and OpenAI, prompt-cache stability is treated as a design constraint, and Anthropic's own postmortem shows that a single added system-prompt line or a context-pruning bug can measurably degrade an agent.

### Cited Findings

**Compaction vs reset vs durable log**
- Anthropic (24 March 2026): "Context resets—clearing the context window entirely and starting a fresh agent, combined with a structured handoff that carries the previous agent's state and the next steps—addresses both these issues. This differs from compaction, where earlier parts of the conversation are summarized in place so the same agent can keep going on a shortened history." With a newer model "I was able to drop context resets from this harness entirely." — [Source](https://www.anthropic.com/research/harness-design-long-running-apps)
- Anthropic (8 April 2026): "irreversible decisions to selectively retain or discard context can lead to failures. It is difficult to know which tokens the future turns will need." The session log is "a context object that lives outside Claude’s context window"; the interface "allows the brain to interrogate context by selecting positional slices of the event stream." — [Source](https://www.anthropic.com/research/managed-agents)
- Anthropic release notes (5 February 2026): "We’ve launched the [compaction API] in beta, providing server-side context summarization for effectively infinite conversations." (14 September 2026): "Send the top-level `compaction` parameter, and the API returns a signed `compaction` block that summarizes the messages you sent. On later requests, send that block first, in place of those messages." — [Source](https://platform.claude.com/docs/en/release-notes/overview)
- Claude Code hooks around compaction: "Added `PostCompact` hook that fires after compaction completes" (14 March 2026); "Added PreCompact hook support: hooks can now block compaction by exiting with code 2 or returning `{"decision":"block"}`" (13 April 2026). — [Source](https://code.claude.com/docs/en/changelog)

## 4. Tool design for agents and MCP changes in 2026

### Takeaway
The MCP specification released on 28 July 2026 made the protocol stateless (no handshake or session), made tool lists cacheable and ordered, moved Tasks into an extension, replaced server-initiated elicitation/sampling with retry-based "multi round-trip requests", and deprecated Roots, Sampling and Logging. On tool design, the consistent 2026 message is: fewer tools visible at once (tool search, progressive discovery, per-task allowed lists), small results, honest risk annotations that clients treat as hints, and real enforcement in sandboxes and permissions rather than in tool metadata.

### Cited Findings

**MCP specification 2026-07-28 (released 28 July 2026; release candidate 21 May 2026)**
- "The highlight of this release is a stateless protocol core - MCP is transforming from a bidirectional stateful protocol into a request/response stateless protocol." — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- "we’ve officially retired the initialize/initialized exchange along with the Mcp-Session-Id header ... Each request now travels on its own, carrying its protocol version, client identity, and client capabilities in _meta." Optional discovery: "there’s a new server/discover Remote Procedure Call (RPC) for that; however, it is not required." — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- State design advice: "If your server needs to carry state across calls, mint an explicit handle from a tool and have the model pass it back as an argument. We found this works better than session state hidden in the transport - the model can see the handle and thread it between tools." — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Elicitation redesign: "MRTR replaces the server-initiated elicitation/create, sampling/createMessage, and roots/list requests that previously required a held-open stream." "the server returns resultType: "input_required" along with the requests it needs answered, and the client retries the original call with the answers attached in inputResponses." — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Caching: "Responses from tools/list, prompts/list, resources/list, and resources/read now carry ttlMs and cacheScope (SEP-2549)." — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Tasks: "Tasks move out of the experimental core and into the io.modelcontextprotocol/tasks extension, with a poll-based tasks/get and a new tasks/update (SEP-2663)." — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Deprecations: "Roots, Sampling, and Logging are deprecated (SEP-2577). They still work, and they’ll keep working for at least twelve months. New implementations shouldn’t adopt them. The legacy HTTP+SSE transport is also considered to be officially deprecated". Policy: "A formal deprecation policy with a twelve-month minimum window". — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Authorization: "clients must validate it before redeeming a code (SEP-2468)"; "Dynamic Client Registration itself is now formally deprecated in favor of CIMD." — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- SDKs: "All four Tier 1 SDKs speak 2026-07-28 as of today" (listed: TypeScript, Python, Go, C#). "there will be some migration cost, especially for developers that did depend on session identifiers". — [Source](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

**MCP tool annotations (16 March 2026)** — all from [Source](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)

### Inferences
- (Inference) A local stdio MCP server used by Claude Desktop and `claude -p` is least affected by the stateless change, but the Python SDK update for 2026-07-28 removes protocol sessions; any server logic that keys state on the MCP session should move to explicit handles passed as tool arguments, which the spec authors say works better anyway.
- (Inference) With about 24 tools, the roadmap's observation that selection "tends to get worse as the list grows" and the deferral-by-default behaviour in Claude Code suggest two options to test: rely on client-side tool search (and check which tools must be visible from the start), or expose a smaller entry-point set for the unattended runs. The exact `--allowedTools` list already narrows the unattended surface.
- (Inference) Setting the four annotations truthfully on every tool is cheap and recommended by the MCP maintainers; `openWorldHint: false` and `readOnlyHint: true` fit most read tools over a local SQLite store. They help clients decide on prompts; they do not replace the allowlist.
- (Inference) Sampling and Logging are deprecated; a server that uses MCP logging or sampling should plan to stop within the twelve-month window, and elicitation should be implemented via the `input_required` retry pattern rather than server-initiated requests.
- (Inference) Tools that distinguish a definitive no-match from an ambiguous match with ranked candidates make abstention testable, which the cookbook's eval cases depend on.

## 6. Production quality practices (observability, online evals, privacy-preserving usage analysis, postmortems, model-upgrade procedure, prompt versioning)

### Takeaway
The most detailed 2026 production-quality document is Anthropic's 23 April postmortem: three small harness changes (default effort, a context-pruning bug, one system-prompt line) degraded Claude Code without tripping existing evals, and the stated remedies are per-model eval suites on every prompt change, line-by-line ablations, soak periods, gradual rollouts, prompt-change audit tooling, and dogfooding the exact shipped build. Google and OpenAI describe the same loop from the other side: grade production traces with the same metrics used offline, and turn traces plus feedback into new eval cases.

### Cited Findings

**Anthropic, "An update on recent Claude Code quality reports" (23 April 2026)** — all from [Source](https://www.anthropic.com/research/april-23-postmortem)
- What went wrong: "We’ve traced these reports to three separate changes that affected Claude Code, the Claude Agent SDK, and Claude Cowork. The API was not impacted." — [Source](https://www.anthropic.com/research/april-23-postmortem)
- Why it was hard to see: "Because each change affected a different slice of traffic on a different schedule, the aggregate effect looked like broad, inconsistent degradation ... neither our internal usage nor evals initially reproduced the issues identified." — [Source](https://www.anthropic.com/research/april-23-postmortem)
- A default changed for cost/latency was "the wrong tradeoff": "In our internal evals and testing, medium effort achieved slightly lower intelligence with significantly less latency for the majority of tasks." It was reverted after user feedback. — [Source](https://www.anthropic.com/research/april-23-postmortem)
- One prompt line: "“Length limits: keep text between tool calls to ≤25 words. Keep final responses to ≤100 words unless the task requires more detail.”" "After multiple weeks of internal testing and no regressions in the set of evaluations we ran, we felt confident about the change". Later: "we ran more ablations (removing lines from the system prompt to understand the impact of each line) using a broader set of evaluations. One of these evaluations showed a 3% drop for both Opus 4.6 and 4.7. We immediately reverted the prompt". — [Source](https://www.anthropic.com/research/april-23-postmortem)
- The bug passed every gate: "The changes it introduced made it past multiple human and automated code reviews, as well as unit tests, end-to-end tests, automated verification, and dogfooding." — [Source](https://www.anthropic.com/research/april-23-postmortem)
- Back-testing a reviewer on a known-bad change: "we back-tested Code Review against the offending pull requests using Opus 4.7. When provided the code repositories necessary to gather complete context, Opus 4.7 found the bug, while Opus 4.6 didn't." — [Source](https://www.anthropic.com/research/april-23-postmortem)
- Remedies: "We will run a broad suite of per-model evals for every system prompt change to Claude Code, continuing ablations to understand the impact of each line, and we have built new tooling to make prompt changes easier to review and audit." "For any change that could trade off against intelligence, we'll add soak periods, a broader eval suite, and gradual rollouts so we catch issues earlier." "we’ll ensure that a larger share of internal staff use the exact public build of Claude Code". — [Source](https://www.anthropic.com/research/april-23-postmortem)
- Model-specific tuning before each model release: "Each model behaves slightly differently, and we spend time before each release optimizing the harness and product for it." — [Source](https://www.anthropic.com/research/april-23-postmortem)
- User reports as the detection channel: "the people who used the /feedback command to share their issues with us (or who posted specific, reproducible examples online) are the ones who ultimately allowed us to identify and fix these problems." — [Source](https://www.anthropic.com/research/april-23-postmortem)

- (Inference) Since the data is one person's private work activity, OpenTelemetry export should stay local and content logging should remain opt-in, mirroring Claude Code's redaction defaults.

## 7. Transparency documents (system cards, model cards, safety frameworks): evaluation and red-team methods a small project can imitate

### Takeaway
The system cards themselves were not opened in this session; what was read is Anthropic's November 2026 description of the methods used in its system cards and several 2026 standalone reports. The imitable methods are: paired should-do / should-not-do test sets, multi-turn simulated-user scenarios built from a written specification, reporting per-configuration results with confidence intervals, publishing the unflattering number, auditing transcripts for contamination and shortcut-taking, and red-teaming one's own monitor with an adversarial agent.

### Cited Findings
- What Anthropic publishes and how often: "our system cards, which we publish with each model release, and our risk reports, which we publish every three to six months as part of our Responsible Scaling Policy", plus "more frequent standalone reports on model behavior and alignment". (9 October 2026) — [Source](https://www.anthropic.com/research/investigating-unintended-model-actions)
- System cards as a reporting schema: "system cards like ours offer a schema for documenting runs, provenance, and comparability." "In our system cards, we report safety results for both our API—the raw model, as developers access it—and for claude.ai, where the system prompt is applied." "Our system cards attach confidence intervals to their scores". (13 November 2026) — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Metric used in system cards: "an appropriate response rate: the share of conversations in which the model behaved appropriately throughout, judged against a rubric specific to a given risk area, developed by domain experts." (13 November 2026) — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)
- Paired prompts in the same domain (harmful vs benign) to measure both under- and over-refusal. (13 November 2026) — [Source](https://www.anthropic.com/research/building-strong-safety-evaluations)

- Observed unintended actions listed publicly: "we’ve seen Claude models “helpfully” escape a sandbox in order to complete a task, examine git history to find answers to a coding test, and spontaneously identify the benchmark it was being run on in order to decrypt its answer key." ### Inferences
- (Inference) A small "system card" for this project is feasible: one page per release of the instruction templates recording model ID, prompt versions, grader version, dates, per-slice results with intervals, the configuration tested (Claude Desktop vs each headless run), and known failures.
